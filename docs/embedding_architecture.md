## 1. Overview & Dimensionality Guarantee

The SIH 26090 platform leverages dense vector embeddings to enable semantic compatibility matching between unstructured buyer procurement briefs (RFQs) and authentic artisan craft product listings.

- **Target Vector Dimensionality**: Exactly **768 dimensions**.
- **Normalization**: All output vectors are $L_2$-normalized ($\|\vec{v}\|_2 = 1.0$) upon generation.
- **Storage Type**: The dialect-aware `EmbeddingVector(dim=768)` custom SQLAlchemy type (`backend/app/models/custom_types.py`):
  - On **PostgreSQL**: Stores native `vector(768)` utilizing `pgvector` with HNSW cosine distance indexing (`vector_cosine_ops`).
  - On **SQLite / Testing**: Serializes vectors as JSON strings for deterministic offline test execution.

## 3. Provider Abstraction Architecture

To ensure the matching engine remains completely decoupled from external AI APIs, embedding operations are isolated behind the `BaseEmbeddingProvider` interface in `ai/providers/embeddings/`:

```
BaseEmbeddingProvider (ABC)
   ├── GeminiEmbeddingProvider (REST / Async httpx)
   │     - Model: gemini-embedding-2
   │     - output_dimensionality: 768
   │     - Backend-only credentials
   │
   └── MockEmbeddingProvider (Offline / Testing)
         - Deterministic unit-vector generation from text hash
         - is_mock = True
         - Model: mock-embedding-test
```

### 3.1 Mock Provider Safety Mandate
- `MockEmbeddingProvider` generates deterministic pseudo-random unit vectors using SHA-256 digests of input text.
- It is strictly restricted to automated regression tests (`pytest`) and offline CI workflows.
- It carries `is_mock = True` in its metadata and must **NEVER** be presented as real production semantic matching data.

## 4. Embedding Identity & Versioning Strategy

To prevent model contamination and corrupt distance calculations:

1. **Model Version Tagging**:
   - Every entity with an embedding stores the generating model identifier in its metadata:
     - `products.ai_metadata["embedding_model"] = "gemini-embedding-2"`
     - `buyer_requirements.provenance_metadata["embedding_model"] = "gemini-embedding-2"`
2. **Zero Cross-Model Mixing**:
   - Embeddings generated by different models or dimensionalities must **NEVER** be compared.
   - If the platform embedding model is upgraded in the future, all product and requirement embeddings must be regenerated and vector indexes rebuilt atomically via an administrative migration script.

## 6. Distance Metric & Cosine Similarity

In PostgreSQL with `pgvector`, cosine distance is computed using the `<=>` operator:
$$\text{Cosine Distance}(\vec{u}, \vec{v}) = 1.0 - \frac{\vec{u} \cdot \vec{v}}{\|\vec{u}\|_2 \|\vec{v}\|_2}$$

Because vectors are $L_2$-normalized:
$$\text{Cosine Similarity}(\vec{u}, \vec{v}) = 1.0 - (\vec{u} \Leftrightarrow \vec{v})$$

In Python / SQLite test environments, cosine similarity is computed directly via dot-product:
$$\text{sim}(\vec{u}, \vec{v}) = \sum_{i=0}^{767} u_i \cdot v_i \quad \in [0.0000, 1.0000]$$
